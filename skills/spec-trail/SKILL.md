# SpecTrail

## 入口与通用约束

一个项目使用一个 Git 仓库，工程文档统一放在根目录 `docs/project/`；多应用、服务或共享包建议采用 monorepo，同仓库 worktree 共用本约定。

用户派发任务时，先检查分支、工作区和相关 Change：

- **无需创建 Change**：纯问答、讨论、只读调查或评审；局部、无歧义的拼写、注释、格式等机械修正，或纠正、补录既有事实的文档描述。后两类必须不改变产品行为、既定要求、架构、共享契约、数据迁移、权限安全或难回退的外部状态。
- **讨论中先行交付**：讨论现有 Change 时，用户提出先实现相关内容、其余方案继续讨论，主动询问是否拆为独立 Change，并简述范围与依赖；已有明确拆分授权时不重复询问。确认后按[创建与规模](#创建与规模)建立新 Change，调整原 Change 范围；仅有实际交付依赖时按[依赖规则](#change-之间的依赖)登记 `dependsOn`，不因执行先后而声明依赖。
- **复用已有 Change**：目标被现有 `active` Change 覆盖时询问用户是否复用。
- **需要新建**：按[创建与规模](#创建与规模)完成简短确认，再建立 Change。

先读取当前仓库 `docs/project/workflow.json`，从协作分支的 changes/archive 按 id 定位 Change，再按 `change.json.branch` 定向读取目标分支。有效的集中 completed 归档直接作为只读历史；进行中的集中副本可以保留旧状态，不作当前进度依据。通过 Git worktree 登记定位本地执行工作区，不扫描所有分支猜测归属。

日常调查与搜索默认排除 `docs/project/archive/`，优先读取当前 Specs、未归档 Change 和实现；仅明确需要追溯历史时，按相关 Change 或主题限定归档搜索范围。ID 查重、依赖及子 Change 状态核对可按 ID 定点读取归档元数据，不扩展为历史正文搜索。

### 分支与协作

- 协作分支由 `workflow.json.collaborationBranch` 指定，推荐名称为 `develop`，不限制项目自定义名称，承担集中讨论与持续交付。主工作区使用项目实际配置的协作分支，不随 Change 或任务切换分支；所有 Change 完成后默认合入这里。保护分支作为正式上线基线，只在用户主动要求时合入或创建 PR，不在普通关闭后反复询问发布方式。
- 新 Change 在协作分支规划，branch 指向自身。实现前从最新协作分支创建独立工作分支（默认 `change/<id>`）、worktree 和执行会话，集中 change.json.branch 登记目标；不替换文件格式、不清理规划目录或镜像执行状态。
- 新 worktree 默认放在主工作区同级的 `<项目名>-worktrees/<工作区名>`，项目名取主工作区目录名，Change 工作区名默认使用 id；已有登记优先复用，用户明确指定路径时沿用，不为统一命名搬动已有工作区。项目的构建和长期服务位置遵循项目约定，SpecTrail 不要求另建服务 checkout。
- 新 worktree 缺少 `.env` 或 `.env.local` 时，先到主工作区查找并按需复用；测试实例使用独立端口和数据目录。
- 工作分支只推进所属 Change；继承的其他记录按集中入口读取。只有所属分支更新完整状态，集中分支仅登记工作分支；任务分支仍可用 `task/<id>/T<n>`，只提交实现和证据。普通 Change 不在协作分支进入实现，多个 xlarge 规划父项可在此聚合与关闭。
- 开始实现前定向同步协作分支与所需工作分支，核对实际 cwd、分支和仓库身份。创建 worktree 或 shell cd 不等于会话绑定；客户端不能准确自动绑定时输出路径和续接提示，由用户打开目标工作区后核验。优先继续已有执行会话；同一 worktree 的多个写入会话需协调。
- 调查和规划可并行；实现边界独立时可使用分支或 worktree。共享行为、Spec、契约、迁移或核心文件重叠时串行协调，small 也不例外。

首次接入按 [Setup 子 skill](./setup/SKILL.md) 提前登记协作/预发布分支（推荐名称 develop）、保护分支和实际平台规则，准备分支与主工作区，再接通提交校验。OpenFolio 接入时直接指定协作分支，读取其项目配置、当前内容、原型策略与 Change 入口，不依赖默认分支配置或保护分支存在。仅支持 workflow v2；未配置协作来源的项目须先完成 Setup，不保留旧工作流运行兼容或全量分支扫描。保护分支只用于发布约束。

## 文档与事实来源

`change.json` 是流程状态的唯一来源，并保存澄清问答；Markdown 保存正文与证据，Git 保存历史。工作台和协作者以推送到中心仓库的 Change 文档为准；本地工作区、暂存区及未推送提交不算已持久化的流程事实，提交标题和历史只供查找参考。

| 位置（相对 `docs/project/`） | 职责 |
| --- | --- |
| `workflow.json` | 协作分支、保护分支与项目配置 |
| `specs/<capability-path>/spec.md` | 当前已实现、验证且仍有效的产品能力与核心技术方案；内容范围见[Specs 同步](#关闭与-specs) |
| `changes/<id>/` | 尚未归档的 Change，含正文、状态和证据；取消的 Change 也保留在这里 |
| `archive/YYYY-MM-DD-<id>/` | 已完成关闭的完整 Change，作为只读历史保存 |

已提交归档的 Change 默认不可修改，包括正文、状态与证据；后续需求或返修创建新 Change。历史勘误仅限用户明确要求，核实事实后在所属分支做最小人工修正，以独立提交说明原因，不改写已推送 Git 历史。

一个 Change 对应一个内聚目标。正文按阶段创建，省略空章节，不生成占位文件、额外索引、TODO、重复状态表或版本计数器，不按固定篇幅或评分凑内容；需求、技术和计划均不写逐文件操作说明。

| Change 内文件 | 内容 |
| --- | --- |
| `requirement.md` | 目标、范围、行为变化、验收；small 另含方案要点 |
| `technical.md` | medium 及以上：实现方案、契约、关键取舍、验证路径 |
| `plan.md` | medium / large：任务定义、执行顺序、验收和验证；xlarge：子 Change 拆分 |
| `research.md` | 按需保存跨会话引用的调查证据与实验结论 |
| `execution.md` | 按任务编号记录实际范围、验证命令与结果、未解决事项；large 必需，其余按需 |
| `review.md` | 评审问题的独立编号、证据、影响与复验结论；large 必需，其余按需 |
| `merge-technical.md` | 实质合码冲突的差异、决策、顺序与验证方法，按需创建 |

Markdown 不维护阶段、完成勾选、任务或审批状态，也不能用正文证据替代 JSON 状态。JSON 只使用已声明字段，文本不填空字符串，尚未发生的可选记录省略。

### 文档配图

medium 及以上 Change 涉及数据结构、时序流程等明显变化时，建议按变更模块分别评估配图，并放入相关需求或技术方案。差异较大的模块分别说明，不以“已有配图”代替判断。图型与数量按需；简单内容不强制配图，small 按需。

图片保存到所属文档旁的 `assets/` 目录，以 Markdown 相对图片链接引用。

## 状态操作入口

分支移交与工作区定位使用 [工作区命令](./references/workspaces.md)，其中 handoff 仅负责 branch 登记。其余常规 `change.json` 创建和修改统一使用主 skill 自带的 [语义命令](./references/state-commands.md)：`node .agents/skills/spec-trail/scripts/change.mjs <command> --change <id>`。调用前按需读取命令说明；不要手写 JSON、用通用 patch 或临时 Python/JS 拼接状态。正文 Markdown 继续直接编辑，下面的字段定义用于阅读与校验。

脚本负责 UTC 毫秒时间、操作前置、失效状态清理和原子写入；Agent 负责实际确认、验证证据、正文一致性与提交推送。历史勘误按[文档与事实来源](#文档与事实来源)处理。共享校验在 `scripts/state-schema.mjs`，hook 与语义命令共用，保持零第三方依赖。

## 读取 Change 现状

读取 `change.json`，核对 `branch` 及当前工作区与已推送版本的差异，依次检查：

1. `status`：仅推进 active；completed 为已关闭的归档历史，cancelled 按取消规则处理。
2. `stage`、`size`、`confirmations`、`rework`：读取相关正文，按[阶段推进](#阶段推进)核对有效确认。
3. `dependsOn`：读取前置 Change 已推送的 JSON，检查[依赖条件](#change-之间的依赖)，不复制其状态。
4. `waitingFor`、任务状态和阻塞原因：small 从 JSON 读任务，medium / large 结合 Plan，xlarge 读取子 Change 状态。
5. `closure`：核对关闭各步的记录与证据。

### 状态字段

```ts
type ISODateTime = string; // 脚本写 UTC 三位毫秒 ISO 时间；读取接受有效的 ISO 8601 时区格式

interface WorkflowConfig {
  schemaVersion: 2;
  collaborationBranch: string; // 推荐名称 develop，可自定义；集中规划、预发布集成和默认合入目标
  protectedBranches: string[]; // 非空、去重，与协作分支角色分离；用户主动要求才发布
  openfolioUrl?: string | null; // 缺失为未询问，null 为无自建服务
  prototype?: PrototypeConfig; // 可选原型接入；缺失表示未选择
}

interface PrototypeConfig {
  status: "disabled" | "pending" | "enabled";
  packagePath?: string; // pending/enabled 必填，disabled 省略；每项目一个包
  hosting?: { provider: "openfolio" | "custom" | "git"; uploadUrl?: string };
}
interface PreviewEntry {
  id: string;
  title: string;
  artifact: { type: "git"; path: string; sourceCommit: string } | {
    type: "hosted"; version: string; url: string; sourceCommit: string; digest: string;
    thumbnails?: { device?: "pc-web" | "ipad" | "mobile"; url: string }[];
  }; // 固定产物引用，详细契约见原型子 skill
  kind: "page" | "component";
  devices?: ("pc-web" | "ipad" | "mobile")[]; // page 必填；去重、非空
  viewport?: { width: number; height: number }; // component 与 devices 二选一，1–4096 CSS px
}

interface Confirmation {
  at: ISODateTime;
  summary: string; // 阶段内容简述，优先 20–40 字符，最多 60 字符、单句；旧记录读取不追溯限制
  source?: string; // 实际确认原话或引用
}

interface Clarification {
  round: number; // 从 1 开始的轮次，同轮共享；正安全整数
  question: string;
  recommendation: string; // 推荐及简短理由
  answer?: string; // 用户最终有效回答或忠实摘要，未答省略，更正覆盖
  source?: string; // 回答来源，按需记录
  withdrawn?: string; // 不再适用的原因，保留原问答
}

interface ClosureStep<Result extends string> {
  result: Result;
  at: ISODateTime;
  summary: string;
}

interface ChangeTask {
  title: string;
  status: "todo" | "doing" | "done" | "blocked";
  branch?: string; // 使用任务分支时填写
  reason?: string; // blocked 时必填，说明解除条件
  verification?: string;
  commitTitle?: string; // 可选查找线索，不作为流程事实
}

interface ChangeState {
  schemaVersion: 1;
  id: string; // 仓库内唯一的小写 kebab-case，与目录名一致
  title: string;
  size: "small" | "medium" | "large" | "xlarge";
  status: "active" | "completed" | "cancelled";
  stage: "requirement" | "technical" | "plan" | "execution" | "close";
  branch: string; // 规划时为协作分支；移交后指向实际工作分支，默认 change/<id>
  clarifications?: Record<`Q${number}`, Clarification>; // 实际问过的问题，编号递增且不复用
  previews?: PreviewEntry[]; // 可省略；记录本次固定交付；项目当前清单位于原型包 prototype.json
  dependsOn?: string[]; // 前置 Change id，去重；全部满足后执行，xlarge 父 Change 不填
  followUpOf?: string; // 同仓库已归档的直接前序，仅表示延续交付，不是执行依赖
  followUpTitle?: string; // 后继声明的独立分组标题，概括共同目标；后续成员默认继承
  parent?: string; // 所属 xlarge 父 Change 的 id
  children?: string[]; // 子 Change id，按 Plan 展示顺序排列且不重复；不表示串行依赖
  confirmations: {
    requirement?: Confirmation;
    technical?: Confirmation;
    plan?: Confirmation;
    merge?: Confirmation & {
      sourceCommit?: string; // 提交 hash：7–64 位小写十六进制
      targetCommit?: string;
      baseCommit?: string;
    };
  };
  tasks: Record<`T${number}`, ChangeTask>; // T1、T2……，编号为正整数
  waitingFor?: {
    kind: "confirmation" | "dependency" | "pause";
    summary: string;
  };
  rework?: { at: ISODateTime; reason: string; approach: string };
  closure: {
    verification?: ClosureStep<"passed" | "failed">;
    acceptance?: ClosureStep<"accepted"> & { source?: string }; // 验收方式按关闭规则；摘要注明方式与依据
    specs?: ClosureStep<"synced" | "not_needed">;
    archive?: ClosureStep<"done"> & { path: string }; // docs/project/archive/YYYY-MM-DD-<id>
  };
  cancellation?: { at: ISODateTime; reason: string }; // cancelled 时必填
}
```

## 创建与规模

### 创建前确认

读取当前对话和必要事实，按核心契约变化、预期实现范围及[任务粒度](#计划与任务)判断规模。局部修改通常为 small；只有实质改变核心契约，或预期实现规模较大时，才升级为 medium 及以上：

| 规模 | 判断（默认参考线） | 必需正文 |
| --- | --- | --- |
| small | 核心契约不变，预计不足 300 行有效实现代码，少于 3 个需联动修改的职责模块；通常一个局部任务 | Requirement，含方案要点 |
| medium | 实质改变核心契约；或预计达到 300 行有效实现代码；或至少 3 个职责模块需联动新增、重写逻辑 | Requirement、Technical、Plan |
| large | 预计达到 1000 行有效实现代码，或至少 5 项需要分阶段集成的独立交付任务 | 上述文档及 Execution、Review |
| xlarge | 需拆为可独立推进、验收和合入的子 Change | Requirement、Technical、Plan，按子 Change 规划 |

判断依据：

- **核心契约**：多个模块或外部调用方共同依赖的稳定接口、持久化数据结构或协议，其关键字段或语义变化需要协同适配、兼容设计或迁移。普通局部配置项和内部参数不自动属于核心契约。
- **有效实现代码**：估算新增或实质改写后的手写生产代码行数，替换同一段代码只计一次；不计空行、注释、配套测试、文档、生成代码，以及纯删除、格式化、搬移、批量替换等机械改动。
- **职责模块与交付任务**：模块按 API、存储、UI 等独立职责计数，不按文件或目录计数；只有需要新增、重写逻辑的模块才计入，同步调用、类型引用不单独计入。任务按[任务粒度](#计划与任务)划分，不把编码、测试、文档等步骤拆成多项凑数。
- 权限、安全、配置等主题，以及一次用户澄清或取舍，不单独构成升级理由；验证与实际操作授权仍按具体影响处理。

默认按满足的最高档位估算。上述数字是事前参考线，不要求逐行审计；临界情况结合职责边界与验证范围判断，偏离默认档位时说明具体依据。xlarge 由是否需要独立子 Change 决定，不仅凭行数升级。

信息不足时先做针对性调查或澄清，按已知影响给出暂定规模，并随证据调整。并行不是 large 的必要条件。简述目标、暂定 `size`、具体判断依据和大致方案，请用户确认启动方向；意图模糊时只追问影响方向的问题。父 Change 已确认的拆分可作为子 Change 的启动确认。

此时无需建立文档或完成全部设计。创建前确认不替代后续阶段确认，不新增 JSON 确认字段。

### 初始化

用户认可后：

1. 按字段约定生成 `id`，核对本地 Change、分支与该 ID 的归档元数据，避免重名。id 表达用户结果，不用纯日期或模糊名称，创建后不变；`title` 可调整。
2. 核对已配置的协作分支与主工作区，先在此规划；不在创建时切换主工作区。
3. 在协作分支运行 `create` 建立目录与初始 JSON，branch 指向协作分支；脚本生成 `active` / `requirement` 和空流程记录。实现前再移交到独立工作分支。
4. 将已有目标、范围、方向、未决问题及外部材料写入 `requirement.md`，继续需求整理。

### Change 之间的依赖

small / medium / large 用 `dependsOn` 声明同仓库的前置 Change，在 Requirement 说明用途，与 `parent / children` 独立。声明时目标必须已建立并推送；依赖不得重复、自指或成环，也不得与父等待子完成的关系构成循环，子 Change 不得依赖其父 Change。

进入 execution 并开始实现前，所有前置 Change 都须满足：**已完成关闭、归档并推送，且所需交付已在当前分支可用**。默认等上游合入协作分支后同步，不要求先发布到保护分支。阶段状态从集中入口解析，不采用当前分支继承的旧副本；集成交付仍需核对，归档存在不代表代码未被回滚。

依赖未满足时可继续调查、澄清和规划；准备执行时仍未满足，保留当前阶段和有效确认，设置 dependency 等待，说明缺少的交付和解除条件。依赖取消、缺失或状态异常均不算满足。解除等待后保留 `dependsOn`；调整依赖时同步用途说明，涉及目标或关键方案变化时按返工规则处理。

### 延续交付

修正或补充某次交付的具体决定或结果时，未归档 Change 在原范围内返工；已归档则新建 Change，通过 `create --follow-up-of <前序 id>` 或 active Change 的 `follow-up --target <前序 id>` 记录延续关系。Requirement 说明具体延续内容，仅属于同一模块或标题相似不构成关联。原目标已改变时独立新建，不为减少列表条目强行挂链。

`followUpOf` 指向同仓库已推送、完成归档的直接前序，不自指、不成环；可形成多跳或多个后继。关联与规模、`dependsOn`、父子关系正交，不增加等待或关闭约束，不合并任务、阶段、验收和归档事实。工作台按关系分组展示独立交付，仍可分别阅读；正文是否描述同一目标由 Agent 核对。

首次建立延续组时，单独生成简洁、单行的分组标题，概括各次交付共同完善的用户目标，不直接复制某次局部修改的标题。用户指定名称时采用原名；各 Change 的 `title` 继续描述本次独立交付。通过 `create --follow-up-of <id> --group-title '<组名>'` 或 `follow-up --target <id> --group-title '<组名>'` 将 `followUpTitle` 保存在后继，不改写前序归档。

后续关联前读取完整延续组及已有组名，默认沿用，包括分叉延续；通常省略 `--group-title`，由关系组继承，不为每次补充重新命名或复制声明。旧组没有独立名称时，在当前后继补充声明；旧记录读取暂用根标题兜底。整体目标发生改变时重新判断是否应独立建 Change，不靠扩大组名强行归组。筛选只影响成员，不改变组名；多个声明不一致时核对共同目标，不能通过改写历史交付标题解决。

active Change 可用 `follow-up --target none` 移除关联，同时清除自身组名声明；更换前序同样清除旧声明，再按新组决定是否命名。已归档记录不自动补写；规则接入时需要关联或命名既有交付，仅在用户明确授权的迁移 Change 中限定目标记录和字段，以独立普通提交保存迁移证据，保留原正文、任务、验收与时间。常规命令不提供归档编辑入口。

### xlarge 父子 Change

父 Change 只维护整体目标、架构、共享契约与拆分，可留在协作分支规划和关闭，不承担产品实现。Plan 列每个子 Change 的 id、目标、边界、依赖、执行顺序和预估规模；JSON 用 `children` 关联，不设实现任务。实际前置依赖由相关子 Change 在 `dependsOn` 声明，父 Plan 汇总，不在父 JSON 声明或向子 Change 自动继承。

子 Change 先在协作分支规划，实现前从最新协作分支分别移交到工作分支，用 `parent` 关联并引用父文档；按 small / medium / large 独立推进、验收、归档和合回协作分支，不再向下拆分。子状态只写入自身 JSON；调整拆分时同步父 Plan 和 `children`，改变整体目标或架构时回到父 Change 的相应阶段返工。全部子 Change 完成或取消后，父项核对协作分支上的交付与整体集成，再关闭。

### 规模调整

规模随证据按上述标准校准；变化时在会话中说明具体契约变化或实现范围，更新 `size`、补齐文档并对齐阶段。small 升级为 medium 时，可一次补齐需求、技术与计划确认后继续受影响实施。规模降低不撤销仍有效的确认，已完成任务保留。

执行中才发现需要拆为子 Change 时，收窄当前范围作为其中一个子 Change，另建父 Change 规划其余部分，按新范围重新核对确认与验证。

## 阶段推进

核对当前规模所需的上游确认仍适用于正文；缺少有效确认时停在最早需处理的阶段，旧 Technical / Plan 保留供修订。

进入 execution 前先按[Change 依赖](#change-之间的依赖)检查；有原型的实现还须先通过[用户原型验收](./prototype/SKILL.md#原型验收)。确认要求和 JSON 更新如下：

| 当前阶段 | 完成条件与后续更新 |
| --- | --- |
| requirement，small | 创建前确认的方向未变，需求、方案要点、验收及任务已写入并推送；直接进入 execution，不记录需求、技术、计划确认 |
| requirement，其余规模 | 用户确认完整目标、范围和验收；记录 `confirmations.requirement`，进入 technical |
| technical，medium / xlarge | Technical 与 Plan 一起确认，xlarge 的 Plan 为子 Change 拆分；同时记录 `technical`、`plan` 确认，进入 execution，不单独进入 plan |
| technical，large | 用户确认方案与必要契约；记录 `confirmations.technical`，进入 plan |
| plan，large | 用户确认整体计划；记录 `confirmations.plan`，进入 execution，无需逐任务审批 |
| execution | 所有任务验证、提交并推送；xlarge 为所有子 Change 完成或取消；进入 close |
| close | 按[关闭四步](#关闭与-specs)完成验收、Specs 同步与归档；归档后才将 status 设为 completed |

## 需求与调查

读取对话、指定材料、相关 Specs 与活跃 Changes，从目标附近的项目规则、代码、配置、依赖和测试调查现状，按需扩大范围。

Requirement 让读者理解问题、交付边界与完成条件。按阅读需要组织章节，同一信息尽量在一处说清；small 补方案要点。

- **目标**：写清谁在什么场景遇到什么困难，以及希望获得的结果；背景只留理解目标必需的现状和依赖。纯工程需求写明确的技术结果，不虚构业务收益。
- **范围与行为**：按用户能力或完整流程说明新增、修改和删除；修改写当前与目标，删除交代替代；涉及兼容或迁移时说明对既有使用和数据的影响。写清实际约束、容易误解的边界及取舍理由；已确认范围均应交付。任务清单、调查过程和通用项目规则各归其位。
- **验收**：覆盖全部已确认交付，可通过测试、演示或观察判断的行为直接作为依据。需要补充时写清条件、动作与预期结果，涵盖相关的异常、边界和不应发生的行为；允许帮助判断的必要复述，避免整段复抄。
- **效果**：已承诺的性能或效果要求须有交付证据，采用有依据的门槛或对比方法与判定方向，不自编指标或用代理指标替代目标。额外的上线后观察按需写方法与时机，默认不作为关闭条件。

产品问题只追问会改变目标、范围、行为或验收的取舍。技术未知项只有在无法通过仓库、一手资料、只读外部状态或必要实验查明，无法可靠推理且实现或验证必需时，才说明缺失内容、影响和建议，向责任人澄清。其他事实继续调查，推断注明依据，未决项说明影响。安装依赖、持久写入、外部操作及高成本实验按已有授权执行；超出范围或有实质副作用时说明目的与影响，已有授权不足时再取得授权。

会话中说明目标、待确认内容、关键假设和限制，吸收反馈后修订正文。small 简述需求、方案与验收后按阶段表执行；其余规模先确认完整需求。

### 分轮澄清

将相关决策组织成**决策树**：每项决策向下连接依赖它的决策，围绕本次目标追问至达成共同理解。**frontier（就绪问题）**是前置已明确、现在可以回答而无需猜测其他答案的全部决策；已有结论直接复用，需求澄清只展开影响目标、范围、行为或验收的分支。技术方案复用本节分轮机制，提问范围与更小额度见[技术问询](#技术问询)。

按轮处理 frontier：预算内将全部就绪问题集中提出；超过本轮额度时优先询问影响最大的，其余保留。逐题编号，给推荐及简短理由，然后等待回答。沿用以下格式，后续编号递增：

```text
❓ **Q1** - **<问题标题>**：<问题及必要选项、取舍>

➡️ <推荐答案及简短理由>

---

❓ **Q2** - **<问题标题>**：<问题及必要选项、取舍>

➡️ <推荐答案及简短理由>
```

每轮回答都重塑决策树：已明确的决策推动 frontier 向外展开，重新计算后再问下一轮。同轮问题不能依赖本轮尚未回答的问题；依赖项留到后续轮次。部分回答只解锁相关分支，未答项保留，推荐和沉默均不算同意；用户可明确选择“全部按推荐，Q2 改为……”。

**事实由 Agent 查，需要用户取舍的决策由用户定。** frontier 需要环境事实时，自行调查；独立调查有并行收益且工具可用时派子 Agent，简短查询直接完成。进行中的调查属于未决前置，只暂缓依赖它的问题，继续询问其他就绪问题，不让用户代查可获取的事实。

以下为单个 Change 的需求澄清预算；[技术问询](#技术问询)使用独立的较小预算，两类互不扣减，不设共用总额度：

| 规模 | 最多轮数 | 每轮最多问题 | 总问题上限 |
| --- | --- | --- | --- |
| small | 1 | 3 | 3 |
| medium | 2 | 3 | 6 |
| large | 3 | 4 | 12 |
| xlarge | 4 | 4 | 16 |

上限不是配额，明确时零追问。一个独立取舍算一个问题，不拆碎或藏题；创建前问题按所属类别计入，各类额度跨阶段、跨会话累计，返工不重置，不为额度升级规模。xlarge 只澄清整体目标、共享边界和拆分，子 Change 按自身规模补齐未决细节，继承结论不重问。

正常收敛须 frontier 为空、相关分支已检查，且没有仍在调查或被额度暂缓的关键缺口，不留下隐含假设。用户要求提前结束时按其要求停止；某类额度用尽时汇总已定结论与关键未决项，停止该类扩展，只有用户明确要求继续才追加该类轮次。另一类仍可在自身额度内询问前置已明确的问题；额度独立不解除依赖，关键缺口影响的推进仍暂停。按[阶段推进](#阶段推进)完成共同理解确认后再实施；small 沿用已确认方向，不额外增加审批。

### 问答记录

用 `clarification-ask / clarification-answer / clarification-withdraw` 保存需求与技术阶段实际提过的问题、推荐和用户最终有效回答，便于回溯遗漏与澄清偏差，不记录用户思考过程。创建时补录创建前问答，Q 编号稳定且不复用，`round` 在整个 Change 中递增，同轮共享，不随阶段重启；未答省略 `answer`，明确更正覆盖原答案，含糊冲突先澄清再更新。撤回保留原问答与原因、不退所属类别额度；实质改变需求或关键方案按返工处理。问答不代替阶段确认。

每题按首次提问所要决定的内容归入需求或技术，只消耗一类额度，不按当前阶段归类。每轮将需求结论写回 Requirement，技术结论写回 Technical（small 写入 Requirement 的方案要点），在对应取舍处注明问题类别并引用 Q 编号；未答或撤回问题也保留类别与引用，跨文档引用、回答引发需求返工均不改变原题归属。较长调查证据放 Research，不复制完整访谈。

分别取两类 Q 记录统计题数、每轮题数和不同 `round` 的数量，不以 `round` 最大值代替已用轮数，不另存计数器。同轮含两类问题时，各自计一轮及本类题数，不重复计题。例如 medium 的需求问题已用 round 1、2，首次技术问题记录 round 3，仍只使用技术第 1 轮。继续会话先读问答与正文，重建决策树和各自剩余额度；命令保存已发生事实，预算在发问前由 Agent 执行，不因超额而漏记。

### 调查与协作资源

复用已有证据，继续核实可调查的缺口。Requirement 只保留影响目标、范围、行为或验收的结论与必要依据，区分材料陈述、推断和项目决策；未验证前提就地说明影响，较长证据放 Research 并引用。与 Specs、实现或已确认需求冲突时显式提出。

影响判断的会话外材料在引用处注明标题与链接，时效影响结论时附读取日期。

当前 Change 产生的外部文档在 Requirement 相关内容处登记链接、用途、目标读者和同步状态；同用途资源优先复用，仓库文档仍为内容来源。外部文档的创建、更新、分享、权限调整和通知均按已有授权执行，不由“同步文档”推导额外授权。

## 技术方案

涉及产品 UI 的 Change，先读 `workflow.json.prototype` 与现有用户选择：缺失时可提议并征求同意；disabled 不重复提议或启用追踪；pending 先完成接入；enabled 复用项目唯一原型包。已有明确同意直接沿用。同意接入后按 [Prototype 子 skill](./prototype/SKILL.md) 初始化，拒绝接入则记录 disabled。已启用时按子 skill 的 UI 规模规则决定询问或先绘制原型；构建、托管、当前清单与固定引用沿用其约定。

medium 及以上基于已确认需求、项目规则和 Research 编写 Technical；small 的方案留在 Requirement。技术澄清与规划阶段只修改文档，不提前修改正式交付代码。

技术未知项遵循[需求与调查](#需求与调查)的提问边界；不影响架构、安全、契约或可行性的任务内局部细节可留待执行。凭证只记录引用、交付与注入方式、环境与权限范围、负责人、就绪及轮换约定，不索要或写入秘密值；原型专用上传地址按子 skill 约定保存到 workflow。

### 对抗式审核：用第一性原理压缩冗余

请你核对一下现在的方向是否正确，有没有过度设计、过度兜底、过度审核、
过度设定边界或者过多 Gate、过多哈希比对、SHA 比对等问题。
以第一性原理推进任务，规避冗余膨胀。

先重述用户真正要解决的问题、当前范围、非目标与最小验收标准。
逐项说明每个复杂机制保护的具体不变量、失败场景或真实需求；
区分「已知风险所需」与「尚无证据的预防性扩张」。

输出：保留 / 合并 / 延后 / 建议删除。每项附证据、影响和最小替代方案。
不因某处出现 Gate、SHA、测试、批准等词就认定它多余。
制品完整性、供应链校验、数据安全和用户明确批准要求应保留。

优先考虑带来最大实际差异的少量修改，不引入新的多层审核来审核审核。
如果建议改变了授权范围或削弱现有保护，必须显式标注。
以上建议随技术方案按既有阶段规则审阅。

### 技术问询

技术问询同时帮助用户理解本次实现重点。每轮先用简短说明串起“如何实现目标、主要复用或新增什么机制、对使用和维护有什么影响”，只介绍理解当前取舍所需的重点；后续轮次补充新信息，不重复完整方案。使用用户能理解的结果与影响解释必要术语，不展开内部代码细节。没有需要用户决定的问题时，也给出实现重点说明，然后按原阶段规则推进；说明本身不占问题额度，也不新增确认步骤。

Agent 先依据已确认需求、项目约定和调查证据形成推荐方案，常规选型与局部实现自行决定。仅将确需用户或责任人取舍、影响体验、数据处理、兼容迁移、成本运维、安全边界或核心可行性的问题放入 frontier；可自行查明的事实继续调查。每题沿用 Q 编号与推荐格式，说明选择带来的实际差异、推荐理由和主要代价，避免让用户只凭框架、算法或数据库名称选方案。例如询问是否接受迁移期间短暂停用写入，同时说明推荐方式及影响。

**数据模型不兼容升级必须由用户取舍。** 先查明并说明受影响的数据与使用方式、可行处理选项及主要代价，询问用户是否接受不兼容、旧数据如何处理，再确定方案；已有明确决定直接沿用，不重复问询。直接接受不兼容是有效选项，按实际需要比较重建、一次性迁移或保留兼容，不默认要求向后兼容，不为假设性的兼容需要擅自加入兼容层、双版本读写或自动迁移等防御性机制。只落实用户选择所需的处理；未明确的取舍阻塞相关方案定稿与实施，不能以推荐或沉默代替回答。small 的方案要点同样适用。

复用[分轮澄清](#分轮澄清)的依赖展开与收敛规则，每轮只问前置已明确的必要问题，收到回答后更新方案及 frontier。技术问询独立使用以下额度，需求澄清用满不影响技术剩余额度：

| 规模 | 最多技术轮数 | 每轮最多技术问题 | 技术问题总上限 |
| --- | --- | --- | --- |
| small | 1（在需求阶段完成，独立计数） | 1 | 1 |
| medium | 1 | 2 | 2 |
| large | 2 | 2 | 4 |
| xlarge | 2 | 2 | 4 |

这是上限而非固定问卷，不重问已确认结论，不把实现重点说明改成理解测验，也不将普通技术细节包装为决策凑题。创建前或需求阶段已问的技术问题同样计入技术额度，跨会话累计，返工不重置、撤回不退额度；不能通过切换阶段或改类重新获得额度。用户提前结束时按其要求停止；技术额度用尽时说明推荐方案、已定结论与关键缺口，停止技术扩展，只有用户明确要求继续才追加技术轮次。需求额度独立保留，未解决的关键缺口仍按技术就绪条件阻塞相关推进，不能以推荐或沉默代替回答。

结论和问题引用按[问答记录](#问答记录)写回对应正文。若回答改变目标、范围、行为或验收，回到 Requirement 按返工规则处理；仅补齐技术证据或在已确认需求内选择实现方式，继续完善 Technical。问询回答不代替方案确认，medium / xlarge 仍与 Plan 一起确认，large 单独确认，small 不新增技术阶段或审批。

### 技术就绪条件

Technical 保留方案、关键取舍、依据和验证路径，不写成任务清单。覆盖本次 Change 相关的以下内容后，才能请求方案确认：

- 每项目标行为的端到端实现路径、数据流及副作用明确，复用适用的现有架构与模式。
- 影响方案选择、核心可行性或验收的事实有足够证据，重要依赖的版本与能力已核对；区分“已验证 / 文档确认 / 合理推断 / 未确认”，不把平台能力存在写成项目已接通。
- 环境与部署差异、配置来源、数据与外部系统契约、安全边界、失败降级及回退明确，涵盖不可逆外部状态；兼容迁移按已确认需要设计，数据模型不兼容升级的处理取舍已有用户决定。
- 外部前置条件的接口、负责人、状态、完成信号、阻塞影响与失败处理明确，不隐藏方案选择，且用户接受其作为 Plan 依赖时，才不阻塞技术确认。
- 验证覆盖验收标准，数据、环境、自动检查与人工验收路径可用或有安排；不存在影响架构、安全、契约或核心可行性的未确认假设或未澄清契约。

未满足时留在 technical 补充调查或必要输入，不进入新 Plan 的确认或执行。补充证据不机械退回需求；目标行为变化才回到 Requirement。large 在技术确认后创建新 Plan，medium / xlarge 将 Technical 与 Plan 一起准备；旧 Plan 可保留供修订。

### 最小正文

引用 Requirement，围绕方案、影响与验证展开，xlarge 说明拆分依据。按阅读需要概括关键取舍与就绪条件，列出影响方案判断的外部前置和未决问题。

## 计划与任务

本节任务粒度适用于所有规模；small 直接在 JSON 列任务，medium / large 使用 Plan，xlarge 的拆分见[父子 Change 约定](#xlarge-父子-change)。

Plan 引用 Requirement 与 Technical，说明交付目标、任务与整体验证；只有需要覆盖默认串行安排时才写执行顺序表。任务按编号列标题、交付、验收和验证方法，与 JSON 的编号、标题一致，初始状态为 `todo`。

### 任务粒度

一个任务对应一个可独立验证的用户场景或明确技术结果，连同必要实现、测试和文档，能在一轮聚焦实现、验证、提交中交付，差异能一次聚焦审阅。不按固定时长、文件数或代码行数设限。

- 包含多个可分别交付的结果、多个独立验证边界或需分批审阅时，继续拆分并列明依赖。
- 只是文件修改、字段或测试步骤，无法单独验证交付结果时，合回对应任务；同一场景必需的异常处理和测试通常不拆开。
- 优先从验收标准拆出端到端场景，不机械按前端、接口、数据库分层。“独立”允许前置依赖，不要求可并行。

优先验证高风险假设，稳定共享契约；前置重构仅覆盖后续交付所必需，保持中间版本可运行。

### 执行顺序

普通 Change 默认按任务编号数值递增串行执行，例如 `T1 → T2 → T10`，不取 JSON 属性顺序或正文排列。前面的任务全部为 `done` 后才能开始或完成后续任务；small 同样遵循此规则，xlarge 按子 Change 组织。

需要并行或特殊安排时，在 Plan 中唯一的“执行顺序”章节提供一份“任务 / 前置任务”表，完整覆盖 JSON 任务，无前置时写“无”。该显式表覆盖默认串行安排；仅有标题或文字说明仍采用默认。表格存在但无效时修正声明，不能忽略它退回默认。前置关系只在此表维护，不在任务正文或 JSON 另设顺序、并行组等字段。

前置已满足且实现边界独立的任务允许并行，不强制同时运行。前置关系既表达交付依赖，也表达执行安排；共享文件、契约或资源等要求串行时，应把先执行的任务列为后者的前置任务。不同执行路径分别按各自前置条件推进，不额外等待无依赖的任务。

显式执行顺序表示例：

| 任务 | 前置任务 |
| --- | --- |
| T1 | 无 |
| T2 | T1 |
| T3 | T1 |
| T4 | T2、T3 |

### 编号与调整

任务在 Change 分支完成验证、记录为 `done` 并提交推送后，冻结编号、定义和完成记录；返修追加新编号，不退回 doing、不复用旧编号。在此之前可以修改、拆分、删除或重排任务，Plan 文档或任务分支上的实现检查点不触发冻结。

任务编号使用正整数 T1、T2……，新增时递增，不复用删除或已用编号。返修在 Plan 和 Execution 中关联原任务，不覆盖历史验证结论。调整后核对 Plan 与 JSON 编号、标题一致；有显式表时核对覆盖完整、任务唯一、前置存在且无自依赖或循环。首次计划应覆盖完整 Requirement，且没有方案级未决项。共享顺序规则在 `scripts/task-order.mjs`，流程命令与工作台共用；执行、任务开始/完成及关闭步骤会重新检查实际安排。

## 执行

开始前按[读取现状](#读取-change-现状)核对状态与有效确认，读取本任务相关的 Requirement、Technical、Plan、Execution、Specs 和项目规则；满足[阶段推进](#阶段推进)的执行条件后再实施。

### 单任务循环

1. 按默认编号串行或 Plan 显式安排选择就绪任务，核对前置链上的任务已完成。用 `task-start` 将任务设为 `doing`。
2. 复用项目模式，完成最小可验证交付并保持中间版本可运行；运行与改动相称的测试、类型检查、构建和必要交互验证；无新变化或疑点时不重复已有成功检查。
3. 对照 Requirement、Technical 与任务验收核对交付，将摘要写 `verification`；较长证据按任务编号写 Execution，记录范围、命令、结果和未验证限制。
4. 验证通过后，用 `task-complete` 记录真实验证，将实现与 `done` 记录一起提交推送，成功后才算完成。提交失败时将工作区和暂存区中的任务恢复为 `doing`，移除尚未成立的 `commitTitle`，保留代码与证据；推送失败按[提交与推送](#提交与推送)处理。

同一分支串行推进，当前任务的实现或状态检查点提交成功后，可切换到其他就绪任务；并行实施使用任务分支与隔离工作区。未完成任务保留 `doing` / `blocked`，可提交真实状态与证据；可运行的中间实现需先调整成独立交付。所有任务完成后按[阶段表](#阶段推进)进入 close。

发现技术缺口时停止受影响实施，设置 `blocked`，在 `reason` 写证据与解除条件，解除后移除原因；继续调查，其他不依赖未确认行为或契约的任务可继续。`commitTitle` 建议用 `<id> T<n>:` 开头，不为记录提交 hash 另造提交。

### 任务分支

只在有并行收益且实现边界不重叠时使用，一个任务至多一个分支：在 Change 分支把任务设为 `doing` 并填写 `branch: task/<id>/T<n>`，提交推送后，从包含前置交付的 Change 分支创建任务分支。

任务分支可有多个提交；验证后普通 merge 回 Change 分支，在合回提交中更新 `done` 与验证摘要，再推送。冲突或涉及其他任务的调整在 Change 分支处理，实质冲突按[合码](#同仓库合码)记录。

## 确认、等待与返工

已有明确确认直接沿用；已确认范围内的推进与普通等价调整无需逐任务审批，只为尚未授权、改变目标、关键方案或风险的决策增加确认。创建后的阶段确认前，准备并推送可审阅结果，在会话中说明待确认事项和对应要求，暂停受影响实施。

确认记录使用实际发生时间与来源，不预填确认，不把当前提交 hash 写进同一个提交。`confirmations.*.summary` 全部写阶段内容简述，优先 20–40 字符、最多 60 字符、单句：requirement 写目标与行为，technical 写机制与取舍，plan 写交付与顺序，merge 写合码策略与关键决策。省略“用户确认”“已同意”“按用户要求”等流程措辞及常规测试、评审、部署清单；确认依据写 `source`，细节留正文。按 Unicode 码点计数，汉字、字母、数字、标点、空格均计入；命令拒绝超长或换行的新摘要，历史读取不追溯限制。

等待时填写 `waitingFor`，摘要说明解除条件，解除后移除。等待与返工不改变 `active` 状态；无等待项不等于已获确认。

返工直接修订原正文和 JSON，不另建返工文档；`rework` 记录当前或最近一轮的时间、原因与处理方式，回到最早受影响阶段：

| 变化 | 确认和任务处理 |
| --- | --- |
| 需求实质变化 | 移除失效的 requirement、technical、plan 确认 |
| 关键技术方案变化 | 保留有效需求确认，移除失效的 technical、plan 确认 |
| 已确认范围内的实现修正 | 保留有效确认，修改未完成任务或追加返修任务；执行中回到 execution，尚在规划时留在对应规划阶段 |

返工时按[规模调整](#规模调整)复核实际影响。清除失效的等待和关闭结果，实现或行为变化后重新执行验证、验收及后续关闭步骤。用户新指令明确确认的部分可直接记录，文字澄清不自动使确认失效；已归档交付按[归档只读约定](#文档与事实来源)处理。

## 关闭与 Specs

归档交付统一由合并提交保存边界；原型沿用该提交，不额外创建保留标签。

按 **整体验证 → 验收 → Specs 同步 → 归档提交** 顺序执行。`closure` 各步按实际结果填写，未完成不预填成功。

### 整体验证

核对确认仍有效、Plan 与 JSON 一致、任务均已验证并提交推送、无未解释阻塞；运行与改动相称的整体验证，覆盖需求、验收、必要失败路径及边界，记录实际证据。xlarge 父 Change 要求全部子 Change 完成或取消，并已集成到协作分支。

| 规模 | 评审要求 |
| --- | --- |
| small | Agent 自查 |
| medium | 默认独立评审，用户可免除 |
| large | 必须独立评审，用户可亲自评审代替 |
| xlarge | 父 Change 核对整体目标与跨子 Change 集成，不重复子 Change 评审 |

独立评审与实现上下文隔离（如 subagent），覆盖整个差异、需求与验收对应及测试证据；在 `closure.verification.summary` 记录评审方式，需跟踪的问题写 Review。

通过记 `verification.result: passed`，进入 active / close，按下述验收规则继续；需等待用户时设置 confirmation 等待并提交推送。失败记 `failed`，按最早受影响阶段返工。

### 验收

small 默认自验收后归档；用户要求人工验收或人工验收提出问题后，该 Change 后续均须用户确认，并在 Requirement 保留此要求。其余规模人工验收。

自验收时逐项核对 Requirement 与交付证据，无未解决验收项后用 `accept --mode agent` 记录通过，摘要注明“Agent 自验收”及依据。

向用户提供实现摘要、验收对应结果、验证证据和已知限制。用户实际验收或明确要求将当前交付归档、合入指定目标分支后，用 `accept --mode user` 记录 `acceptance.result: accepted`，摘要引用原话或附 `source`；已有明确授权直接沿用，不再次索要同一确认。Agent 自查、测试通过和事先“做完就行”的笼统指示不等于用户验收。

等待人工验收时保持 active / close，不同步 Specs、不归档；原范围内的调整继续在原 Change 按[返工规则](#确认等待与返工)处理。

### Specs 同步

Specs 以任意深度的稳定业务能力树组织，完整相对路径是能力身份，每段使用小写 kebab-case；含 `spec.md` 的路径代表能力，其余是命名空间。父级写共同行为和边界，子级写细节；不按页面、技术层或源码目录机械拆分。核心技术方案写在其约束的能力下，跨能力方案可用独立路径；移动或重命名时同步引用。

以最终验收实现为准，重读当前 Specs，结合 Requirement 中新增、修改、删除的行为与长期核心方案，按能力路径合并；small 的方案取自 Requirement，其余取自 Technical：

- 只描述已实现、验证且仍有效的产品行为，以及架构、共享契约、数据模型、安全边界等长期约束；未来目标留在 Change。
- 用当前时态，不放 Delta、任务状态、评审过程或变更日志。普通技术修正、重构、性能调优、实现细节和恢复既有行为的缺陷修复不写入 Specs。
- 保留无关内容，涉及 API、数据或共享契约时核对对应文档；发现冲突或实现不一致时停止归档。
- 仅纠正文档对当前实现的错误描述或补录既有行为时可直接改 Spec；改变实现则通过 Change。新项目首次 Change 关闭时才产生第一批已实现 Specs。

同步后记 `specs.result: synced` 和影响范围；无需变更时记 `not_needed` 并说明理由。

### 归档

前三步成功且证据仍适用后，将完整目录移动到 `docs/project/archive/YYYY-MM-DD-<id>/`，目标冲突不能覆盖，并确认源目录已不存在、目标材料完整。记录 `archive.result: done` 与 `path`，设置 `status: completed`、`stage: close`，移除等待项，将 Specs、最终 JSON 和目录移动一起提交推送。

尚未提交归档而需再改实现时，先移回 changes、恢复 active 并返工；已提交后按[归档只读约定](#文档与事实来源)处理。

默认合入协作分支时仅核对所属 Change 已关闭及实际交付范围；其他 Change 的继承规划副本可以保留，见[合码](#同仓库合码)。

归档前同步协作分支并验证；xlarge 规划父项先用 `workspace.mjs handoff` 转入独立关闭分支。归档提交推送后，按[集成与清理命令](./references/integration.md)生成、推送并核实合并提交，更新项目服务后默认清理原始分支与 worktree，无需再选择目标。保护分支合入或 PR 仅由用户主动要求触发；归档不授予保护分支发布授权，创建 PR 不授权合并 PR。已集成到协作分支的有效归档可直接阅读，branch 保留历史归属，不为已完成历史强制保留工作分支。

## 取消 Change

用户取消时设置 `status: cancelled`，记录 `cancellation.at`、`cancellation.reason`，移除等待项，保留当前阶段、任务、正文与代码。不回滚、不补齐剩余文档或任务、不同步 Specs、不归档。

只提交推送取消记录及必要说明，已有未提交实现原样保留并向用户说明，不伪装为完成任务或混入取消提交。随后冻结该 Change 分支及其任务分支：保留在中心仓库，不删除、不开发、不合入；只允许完成取消检查点或修复其提交、推送失败，不能把 cancelled 改回 active。

继续其他工作从最新协作分支规划并移交到独立 worktree，保留取消分支和未提交现场；转用代码在新 Change 下重新确认和验证。取消 xlarge 父 Change 时确认未完成子 Change 是否一并取消。

协作分支中取消仅规划的 Change 只冻结该记录，保留取消记录和发现入口，不冻结其他规划。移交后取消仍在工作分支记录；集中入口继续指向它，清理分支必须同时检查活动和取消入口。

## 同仓库合码

合码本身不创建新 Change，仅处理同一 Git 仓库内分支或 worktree。

| 方向 | 方式与条件 |
| --- | --- |
| 任务分支 → Change 分支 | 普通 merge，不 squash；任务已验证，合回后更新任务状态 |
| 协作分支 → Change 分支 | 在独立 worktree 内 merge；Change 分支未取消 |
| Change 分支 → 协作分支 | 归档后一次 `--no-ff` 合并，保留原始提交；仅交付一个 Change |
| 协作分支 → 保护分支 | 用户主动要求后普通 merge 或创建 PR，保留提交历史与规划文档 |
| 保护分支 → 协作分支 | 回流独立修复时使用 `--no-ff`，保留协作分支 first-parent 历史 |

先只读核实仓库、源目标分支、worktree、workflow 分支职责、两侧提交、merge base、工作区与相关 Change / Specs，定向 fetch 后以中心仓库提交为准。用 diff、log 和可用的 merge-tree 评估文本与语义冲突，不在含用户修改的工作区试合并。

普通可机械处理的差异按既定方案解决。有大量冲突、行为分歧或共享契约变化时，在尚未归档 Change 的 `merge-technical.md` 记录确切源 / 目标 / base 提交、需保留的行为、冲突决策、顺序、失败恢复和验证方法。只对新决策请求确认，用 `confirmations.merge` 记录时间摘要，可附三侧提交。实质改变需求或方案时按返工规则更新原文；新的实现修正追加任务。

先在 Change 工作区同步协作分支、解决冲突并验证，再归档推送。使用[集成命令](./references/integration.md)从最新远端协作提交创建 M，即使可快进也保留双亲合并；标题注明 Change，末尾使用唯一 `SpecTrail-Change: <id>` trailer。整体 diff 为 `git diff M^1 M`，不在 change.json 保存 M。协作并发推进时重建未发布候选，不把远端合到旧候选上，不强推协作分支。主工作区仅安全快进，不承担冲突处理。

默认集成保留其他 Change 的规划目录；M 相对第一父提交只新增本 Change 的归档，归档子树与第二父提交一致。本期不处理提前分批合入或补造历史合并；已归档内容不可为解冲突而改写。xlarge 父项的 M 仅表示父项交付，各子项保留自己的 M。

保护分支发布时固定已验证的源、目标提交，在隔离候选中普通 merge，保留提交历史及 `docs/project/changes/`；PR 合并也保留历史。规划文档进入保护分支不表示 Change 已完成或对应能力已上线。不再过滤规划、squash 或重建单父交付快照；核实远端保护分支包含源提交后才报告合并完成。正式上线以保护分支为基线，部署沿用项目约定；部分 Change 发布另按用户明确范围处理，不自动推断组合。

已有授权且检查通过后合并；未授权时先准备具体可审阅结果，再请求最终授权。最终集成证据留在 Git / CI，不改只读 archive。目标变化需实质返工时，从最新协作分支规划新 Change；旧交付尚未合入时可把已归档提交纳入新分支，再验证与归档。

## 提交与推送

使用工作流推进 Change 即包含 Change / 任务分支上的提交推送。文档形成可审阅版本、收到确认、阶段调整、阻塞、任务完成、取消和归档都及时形成检查点，本轮结束前提交。同轮相关正文与状态一起提交，只暂存相关文件，保护用户修改，不做空提交、不跳过 hooks。

每个检查点提交后立即推送同名分支，请求审阅或阶段确认前相关文档应已推送；创建前简短确认除外。提交失败保留工作区，用 `task-retry` 恢复尚未提交的任务状态，见[执行](#执行)；推送失败保留本地提交、修复并重试，如实报告未同步。

合码方式见[同仓库合码](#同仓库合码)。Change 与任务分支不 squash、不改写已推送提交，未推送的本地提交可 rebase。远端 M 核实及项目交付验证后默认清理来源，先远端分支、再本地 worktree、最后本地分支。保护新增提交、活动或取消入口、主工作区、未保存与未知忽略文件；Agent 核实会话及服务占用，不能确认时保留并报告。合入与逐对象清理结果分别说明，重试不重复集成，也不回填归档。默认集成协作分支沿本规则执行；保护分支合入、PR 或正式发布须由用户主动要求。

完成操作后说明实际结果、位置、验证及提交推送状态；关闭时报告 Specs 范围与归档提交，取消时说明代码保留、分支冻结与取消记录。未完成、未验收或未推送时不宣称完成。
