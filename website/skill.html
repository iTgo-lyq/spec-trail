准备开始

在目标项目根目录安装。

需要 Git、能操作本地文件和 Git 的编码 Agent，以及 Node.js 24。安装后，主 Skill、接入工具、原型子模块和共享脚本保存在项目的 .agents/skills/spec-trail/。

{{INSTALL}}

安装命令为 Codex 或 Claude Code 配置入口。工作流文件可以随项目提交，协作者从同一份仓库约定开始。

接入项目

让 Agent 核对项目现状。

安装完成后，在项目对应的 Agent 对话中发送：

使用 $spec-trail 为当前项目接入工作流，检查默认分支和现有提交校验。

Agent 会登记实际守护分支，检查 Skill 文件与运行环境，并沿用项目现有的提交校验方式接入验证。新克隆的协作者也需要按项目约定启用本机提交入口。

第一项任务

给出目标，也给出验收期待。

在已经接入的项目中，直接说明你想完成的改动。例如：

使用 $spec-trail 实现订单 CSV 导出：支持当前筛选结果，导出字段与列表一致。先整理需求和验收条件，再推进实现。

Agent 按实际范围确定 Change 规模，整理文档，确认需要你决策的事项，再推进任务。告诉 Agent 你的部署、验证和合入约定，让它使用真实证据完成交付。

流程与规模

按改动规模，选择需要的步骤。

规模适用情况主要记录
Small目标与验收清晰，通常一个独立任务需求与方案要点、任务状态及验证
Medium需要少量独立任务与明确计划需求、技术方案、计划与执行证据
Large多个可独立验证的交付，范围较大完整方案、计划、执行及独立评审记录
XLarge需要拆为可独立推进和验收的子 Change父 Change 方案与子 Change 交付

从需求到归档

  1. 整理目标、边界、行为变化和验收条件。
  2. 形成技术方案与验证路径，确定任务和依赖。
  3. 逐任务执行，保留代码、状态与实际验证证据。
  4. 完成验证和验收，更新 Specs，再归档 Change。

关键取舍与必要确认由 Agent 按流程处理。任务规模、依赖和验证证据决定推进方式。

记录放在哪里

每类文件，负责一类事实。

SPECS当前能力

已经实现、验证且仍有效的产品行为与核心方案。

CHANGES正在发生的改动

目标、方案、任务、流程状态和交付证据。

ARCHIVE完整的历史

已完成 Change 的正文、验收依据与固定原型引用。

docs/project/
├── workflow.json
├── specs/<capability>/spec.md
├── changes/<change-id>/
│   ├── change.json
│   ├── requirement.md
│   └── 按任务规模创建的方案与证据
└── archive/YYYY-MM-DD-<change-id>/

change.json 保存流程状态，Markdown 保存正文与证据，Git 保存历史。Agent 使用语义命令更新状态；提交并推送后，协作者和工作台才能读到同一份工程事实。
